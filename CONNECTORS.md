# Building a connector for Voucher Captain

A connector is a separate plugin that redeems Voucher Captain vouchers for something outside the WooCommerce cart: a course, a membership, a ticket, a service. Voucher Captain stays generic – no course or LMS fields in its core. The connector owns its service; Voucher Captain owns the voucher value.

A complete, tested reference implementation is in [`examples/vcap-example-connector`](examples/vcap-example-connector/vcap-example-connector.php) (CI: `tests/example-connector-integration.php`). API details: [API.md](API.md). Ledger states: [STATE_MACHINE.md](STATE_MACHINE.md).

### Event timing (transactions)

Voucher Captain changes balances and states in short database transactions with a row lock (`SELECT … FOR UPDATE`). All of them run through one helper (`VCAP\Db::begin()` / `commit()` / `rollback()`, or `Db::transaction( callable )`; nested calls use savepoints). The contract for listeners (D6):

- **Side-effect actions fire only after a successful COMMIT.** `vcap_voucher_updated`, `vcap_voucher_event`, `vcap_voucher_created`, `vcap_voucher_deleted`, `vcap_voucher_expired`, `vcap_voucher_redeemed`, `vcap_redemption_reserved` / `_released` / `_refunded` / `_reversed`, `vcap_store_credit_changed`, `vcap_gift_card_topped_up` and `vcap_ticket_checked_in` are buffered while a transaction is open and dispatched once, in the order they happened, after the outermost COMMIT. On ROLLBACK they are discarded – a listener never reacts to a change that did not happen. Outside a transaction they fire immediately, as before. [docs/HOOKS.md](docs/HOOKS.md) marks these actions with *after COMMIT*.
- **Listeners see committed data.** When the action runs, other connections already see the new balance or state, and no row lock of Voucher Captain is held. A listener may make remote calls, start its own transaction, or call `vcap()->redemptions` / `VoucherRepository` again (their actions follow that transaction's own COMMIT). A listener can no longer commit or roll back the change that fired it.
- **Arguments are snapshots.** A `Voucher` argument shows the voucher as it was saved at that point; several saves in one transaction fire several actions, each with its own state.
- **A failing listener does not undo the change.** The data is committed when the listener runs: an exception thrown by a listener is logged (WooCommerce → Status → Logs, source `voucher-captain`) and the remaining listeners still run – for buffered actions and also for actions fired outside a transaction (M12-05). It never reaches the caller of the booking. Repair your side from the ledger (`vcap_voucher_event` history) or `vcap()->redemptions->get( $key )`.
- **Deciding filters cannot be deferred.** `vcap_redemption_allowed` and `vcap_redemption_target_available` decide whether a redemption happens, so they run synchronously. `reserve()` evaluates them **before** it locks the voucher row (on the voucher as read then; status, balance and owner are checked again under the lock); `check()` holds no lock. They may still run while a caller's transaction is open (e.g. a connector that calls `reserve()` inside its own transaction). Keep them fast and local: no remote calls that can take long, no own transaction, no writes – answer from data you already have and do slow checks before calling `reserve()`.

Your own code: when you call `reserve()` / `commit()` inside a transaction of your plugin, use `VCAP\Db::transaction()` (or `Db::begin()` / `Db::commit()`) instead of a raw `START TRANSACTION`, so Voucher Captain's work nests as a savepoint and its actions wait for your COMMIT. A raw `START TRANSACTION` inside an open transaction commits it implicitly (MySQL/MariaDB). Voucher Captain's bookings read the voucher row with a locking read (`VoucherRepository::get_for_update()`), so they book from the latest committed balance even when your transaction read the voucher before (M12-04). If the database rolls back your whole transaction while Voucher Captain's savepoint is open (deadlock), the remaining levels can only be rolled back: `Db::commit()` returns false and `Db::begin()` opens nothing until your outermost level is rolled back – retry the whole transaction then.

## 2. Redemption flow (copy this)

1. **Derive a stable key** from what identifies the request, e.g. `myplugin:{user}:{hash(code)}` or `myplugin:grant:{grant id}`. Store it before calling Voucher Captain. A double click, a reload or a retry after a timeout must reuse the same key.
2. **`reserve( $code, [ 'key', 'target', 'user_id' ] )`** – locks the voucher. Same key + same request ⇒ same answer while the redemption is `reserved` or `committed` (`replayed: true`); once it was released or expired the key answers `vcap_redemption_released`. Register server-side key prefixes (e.g. `myplugin:grant:`) with `vcap_internal_redemption_key_prefixes`, so nobody can claim them over REST in advance.
3. **Deliver your service idempotently**: store the redemption key with what you grant; if the key is already there, do nothing.
4. **`commit( $key )`** – final. Repeating it is harmless.
5. Only if you cannot deliver: **`release( $key )`** – the voucher becomes usable again.

### Errors and retries

| Answer | What to do |
|---|---|
| `vcap_temporary_failure` (503) | Keep the key, retry later (Action Scheduler) with the **same key** |
| Your service fails (timeout, outage) | Keep the reservation, retry steps 3–4 later. Give up after a limit and `release()` |
| `vcap_reservation_missing` on commit | The reservation expired (lifetime setting, default 15 min) and was released. Revoke anything you granted for this key; ask the user to redeem again |
| `vcap_cancelled` on commit | The voucher was voided while reserved (purchase refunded). Revoke, `release()`, tell the user |
| `vcap_already_redeemed` on reserve | Check whether *you* hold the grant for this key (completed by a retry) – then it is a success |
| `vcap_login_required` (403) | A personal voucher and no verified identity: ask the customer to log in with the masked address from the message, then retry |
| `vcap_redemption_released` (409) on reserve | The reservation under this key was released or expired: nothing is reserved. Revoke anything granted for the key, forget it and – if the user wants to redeem again – use a **new** key (the example connector appends an attempt number) |
| Any other error | Show the message; nothing was reserved |

Retry jobs read the current state with `get( $key )` and continue from there: `reserved` ⇒ deliver + commit; `committed` ⇒ make sure the grant exists; `released` ⇒ revoke and forget the key. Make the reservation lifetime longer than your longest retry window, or expect `vcap_reservation_missing`.

## 3. Refunds and cancellations

| When | What Voucher Captain does | What the connector should do |
|---|---|---|
| Purchase order refunded/cancelled **before** any redemption | Voucher is voided (setting *Void vouchers on refund*, default on); `check`/`reserve` answer `vcap_cancelled` | Nothing |
| Purchase order set to *Cancelled* by hand (no refund recorded) | Only unused vouchers are voided; vouchers already used (redeemed in the shop or by a connector, partly spent, reserved) stay as they are – an order note names them | Nothing; the merchant voids by hand if money is paid back |
| … **while** a reservation is open | Voucher is voided; `commit()` answers `vcap_cancelled`; `release()` keeps it voided | Revoke, release, inform the user |
| … **after** the redemption was committed | Full refund: voucher is voided (event `voided`); the redemption stays committed | Your policy: keep the access (service already delivered) **or** revoke it on `vcap_voucher_event` / `voided`. Document it in your terms. The example connector revokes. |
| Partial refund of the purchase order (refunded quantity of a voucher line) | As many vouchers of the line as the refunded quantity covers are voided (event `voided`, note "Partial refund #…"): unused ones first, then partly spent gift cards (their unspent value is what is paid back). Vouchers **used up completely** (redeemed single-use vouchers, gift cards without balance) are **never** voided by a partial refund – their value was not refundable; an order note names them. A topped-up gift card keeps its topped-up value (event `purchase_refunded` instead of `voided`). A refund amount without quantities voids nothing | A `voided` event after a partial refund always concerns a voucher you have not committed (or only partly spent): revoke open reservations, keep completed services |
| The service is refunded/cancelled in the connector | Nothing automatic | If the customer should get the voucher back, ask the merchant to *Reactivate* it (admin) – committed redemptions are never undone automatically |

## 4. Group packages: per seat or per package?

Voucher Captain issues **one voucher per unit**: quantity × *PDFs per item* (product setting) – see `vouchers` in the line snapshot. Decide in the connector:

- **Per seat** (recommended): one voucher unlocks one seat. Sell the package with *PDFs per item* = number of seats; each recipient redeems their own code. Refunds and transfers work per seat.
- **Per package**: one voucher unlocks the whole package. Keep *PDFs per item* = 1 and store the seat count in your target (e.g. `myplugin:package:5`) or read it from `order_lines()` (`voucher_line` + product). Partial refunds of a package must then be handled by the connector.

Discount codes and promotions always apply to the order line (the package price), never per seat.

## 5. "Customer owns product X" and external member prices

Voucher Captain does not know what a customer owns in another plugin. Use the existing hooks:

- **Only owners may redeem / only non-owners may redeem**: refuse in `vcap_redemption_allowed` (`$user_id` is the authenticated user).
- **Discount codes only for owners**: `woocommerce_coupon_is_valid` (throw an `Exception` with your message), or a promotion customer group via a user role your plugin assigns (Vouchers → Promotions → *Customer groups*).
- **Member prices or bundle prices from another plugin**: promotions and coupons are calculated on the cart price that plugin produced. If a promotion must not stack on member prices, limit it to a customer group without members (user roles), or remove the member-priced items in `woocommerce_coupon_get_items_to_apply` (priority > 20). To keep promotions apart from discount codes, untick *Also applies when the customer uses a coupon code*. Voucher products are never discounted unless the merchant allows it.
- Gift cards and store credit always pay the remaining amount **after** all discounts (`woocommerce_coupon_sort`).

## 6. API versioning policy

- The public API is: `vcap()->api_v1`, `vcap()->redemptions`, `vcap()->read` and the functions `vcap_read_*()` (since contract 1.2.0), the REST namespace `vcap/v1`, the `VCAP\Contracts\*` interfaces, the hooks listed in API.md/CONNECTORS.md (all prefixed `vcap_`) and the documented order/coupon meta (`_vcap_line`, `_vcap_fields`, `_vcap_voucher`).
- Within **v1** changes are additive only: new methods, new optional arguments, new array keys, new hooks, new error codes for new situations. Existing keys, error codes, HTTP statuses and hook arguments keep their meaning.
- Native parameter and return types on the `final` v1 classes may be added within v1 when they match the documented types. Native return types on the `VCAP\Contracts\*` interfaces are **not** added within v1: implementations would have to change their signatures, so that is a breaking change for v2.
- Breaking changes get a new version side by side (`api_v2`, `vcap/v2`). The previous version stays available for at least two minor releases and six months, with a deprecation notice (`_deprecated_function` and a changelog entry).
- **Contract version** (since plugin 1.2.0): the constant `VCAP_CONTRACT_VERSION` names the version of this public contract, independent of the plugin version. Major = API generation (`1` = `api_v1`, `vcap/v1`); the minor version rises with every release that adds hooks, methods or arguments; a patch version only clarifies. An add-on checks it once instead of probing single hooks: `defined( 'VCAP_CONTRACT_VERSION' ) && version_compare( VCAP_CONTRACT_VERSION, '1.1.0', '>=' ) && 1 === (int) VCAP_CONTRACT_VERSION`. The constant is not defined in plugin 1.1.0; treat "not defined" as contract 1.0.0. History:

  | Contract | Plugin | Added |
  |---|---|---|
  | 1.0.0 | 1.1.0 | first public contract: `vcap()->api_v1`, `vcap()->redemptions`, REST `vcap/v1`, `VCAP\Contracts\*`, the hooks marked "1.0.0" and "1.1.0" in docs/HOOKS.md |
  | 1.1.0 | 1.2.0 | the hooks marked "1.2.0" in docs/HOOKS.md, among them the add-on extension points `vcap_admin_menu`, `vcap_voucher_links`, `vcap_voucher_issued_standalone`, `vcap_counter_limits`; `vcap_voucher_event` with source and user id; `vcap()->issuer->issue_standalone()`; action `vcap_loaded` |
| 1.2.0 | 1.2.0 | read functions `vcap_read_voucher()`, `vcap_read_gift_card()`, `vcap_read_store_credit()`, `vcap_read_redemption()`, `vcap_read_redemptions()`, `vcap_read_order_vouchers()` and the service `vcap()->read` (`VCAP\API\V1\ReadService`): state by record id without code or personal data (API.md → "Read functions"). Plugin 1.2.0 is not released yet; the read facade got its own minor version so that an add-on can tell a build with it from an earlier 1.2.0 build (contract 1.1.0) |

- The first plugin version of every hook is in the "Since" column of docs/HOOKS.md (generated; a new hook needs `@since` in its doc comment, `php bin/hooks.php --check` fails otherwise). Every public method carries `@since`. Everything else (classes without a documented contract, database tables, private meta) is internal and may change in any release – never query Voucher Captain's tables directly. Everything else (classes without a documented contract, database tables, private meta) is internal and may change in any release – never query Voucher Captain's tables directly.
- Connectors should check `defined( 'VCAP_VERSION' ) && version_compare( VCAP_VERSION, '1.1.0', '>=' )` and `function_exists( 'vcap' )` before registering hooks. Since 1.2.0, `vcap()` exists only once Voucher Captain has booted (WooCommerce active in a supported version), so `function_exists( 'vcap' )` from `plugins_loaded` priority 11 on is a reliable check; better, register in the action `vcap_loaded` (argument: the running `VCAP\Plugin`), which fires exactly then. `VCAP\Plugin::ready()` tells whether the plugin booted; `VCAP\Plugin::instance()` throws a `LogicException` without a supported WooCommerce.

## 7. Checklist for a connector release

- [ ] Stable key per request, stored before `reserve()`
- [ ] Idempotent grant (key stored with the grant)
- [ ] Retry job with limit; `release()` when giving up
- [ ] Handling of `vcap_reservation_missing`, `vcap_cancelled`, `vcap_already_redeemed`
- [ ] Refund policy after redemption decided and documented
- [ ] Own channel registered; merchant documentation tells them to tick it
- [ ] Personal vouchers: `email_verified` passed only for identities your plugin verified; `vcap_login_required` handled
- [ ] Listeners of `vcap_voucher_event` & co. expect to run after the COMMIT; `vcap_redemption_allowed` / `_target_available` stay fast and local (see *Event timing*)
- [ ] Two-plugin integration test (Voucher Captain + connector) in CI, including a forced outage
